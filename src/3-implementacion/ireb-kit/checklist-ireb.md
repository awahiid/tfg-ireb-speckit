# IREB Quality Checklist for Requirements

> **Purpose**: Generated by `/speckit.checklist` in Flow B (IREB-enhanced).
> **Based on**: IREB CPRE Foundation Level Handbook [1],
> ISO/IEC/IEEE 29148:2018 §6.2.2 [2], INCOSE Guide for Writing Requirements [3].
> **Usage**: This checklist is provided to the SpecKit agent during
> `/speckit.checklist`. The agent validates each requirement in the
> specification against every criterion.

---

## Block A — Identifiability & Management

### R1. Unique Identifier
Each requirement has a unique, stable, non-reusable ID with format
`REQ-[DOMAIN]-[NNN]`.

> *Reference*: IREB defines unique identification as a basic attribute
> for traceability and change management [1, §Requirements Documentation].
> ISO 29148 requires unambiguous identification of every requirement
> within the specification [2, §6.2.2].

- [ ] All IDs follow the `REQ-[DOMAIN]-[NNN]` pattern
- [ ] No IDs are duplicated
- [ ] IDs are not re-used from deleted requirements

### R2. Valid Classification
The Type attribute contains exactly one of: Functional, Quality, Constraint.

> *Reference*: IREB distinguishes three main types of system requirements:
> functional requirements, quality requirements, and constraints [1,
> §Requirements Types]. ISO 29148 establishes different categories of
> requirements within a specification [2, §5.2.1].

- [ ] Every requirement has a non-empty Type field
- [ ] All Type values are one of: Functional, Quality, Constraint
- [ ] No requirement uses ad-hoc types (e.g., "Important", "Security")

### R3. Traceable Source
The Source field documents the origin with sufficient detail to locate
the original evidence (version, date, URL, identifier).

> *Reference*: IREB defines Source as a fundamental attribute to support
> traceability toward the origin [1, Glossary]. ISO 29148 contemplates
> documentary sources as valid origins of requirements [2, §6.3.1].

- [ ] All requirements have a non-empty Source field
- [ ] Sources include at minimum: document type, version/date, identifier
- [ ] No sources are generic (e.g., "various sources", "team discussion")

### R4. Assigned Priority
The Priority attribute contains exactly one of: High, Medium, Low.

> *Reference*: IREB includes priority as an attribute to support
> negotiation and scope management [1, §Stakeholder Priority].
> ISO 29148 contemplates priority as a requirement management attribute [2].

- [ ] All requirements have a non-empty Priority field
- [ ] All values are one of: High, Medium, Low
- [ ] Priority distribution is reasonable (not all "High")

### R4b. Documented Dependencies
If the requirement has functional dependencies on other requirements,
these are documented in the Dependencies field.

> *Reference*: IREB defines traceability between requirements as an
> attribute to manage dependencies and analyze impact of changes [1,
> §Traceability].

- [ ] Dependencies field is present (even if empty)
- [ ] Dependencies reference valid REQ-IDs
- [ ] No circular dependencies

### R4c. Assigned Module
The Module attribute references a subsystem or functional component.

> *Reference*: Organization by modules is standard practice in
> specifications for complex systems [2, §Requirements Organization].

- [ ] All requirements have a Module field
- [ ] Module names are consistent across the corpus

## Block B — Writing & Verifiability

### R5. Formal Structure
The description follows the pattern: "El sistema deberá [verb] [object]
[condition]". Condition may be omitted if the behavior is precise without it.

> *Reference*: INCOSE recommends uniform structure to reduce ambiguity
> and facilitate verification [3, §Structure]. ISO 29148 requires
> requirements to be clear and unambiguous [2, §6.2.2].

- [ ] All descriptions start with "El sistema deberá"
- [ ] The structure has verb + object (+ optional condition)
- [ ] No requirement starts with passive voice or vague phrasing

### R6. Single Obligation
The requirement describes exactly one main behavior. Conditions are
allowed on that behavior, but not two independent action verbs.

> *Reference*: INCOSE establishes that requirements must be singular
> [3, §Singular]. A condition is not an additional obligation.

- [ ] Each description contains exactly one action verb
- [ ] Conditions are attached to the main action, not independent
- [ ] No requirement uses "and" to chain two independent actions

### R7. Observable Verb
The main verb describes behavior that can be observed or measured directly.

> *Reference*: INCOSE recommends verbs that allow objective verification
> of compliance [3, §Characteristics of Individual Requirements].

- [ ] Verbs are from the observable set: generate, register, reject,
  return, prevent, notify, calculate, validate, block, store, send
- [ ] No ambiguous verbs: manage, handle, process, support, facilitate,
  improve, provide, enable, allow, ensure

### R8. Absence of Critical Ambiguity
The statement contains no subjective terms or expressions open to
multiple interpretations that affect verification.

> *Reference*: ISO 29148 and INCOSE require unambiguous requirements.
> Domain-specific technical terminology is acceptable; everyday
> subjective language is not [2, §6.2.2] [3, §Unambiguous].

- [ ] No subjective terms: fast, efficient, intuitive, adequate,
  appropriate, sufficient, user-friendly, robust, reliable
- [ ] If a subjective term appears, it is justified as domain-standard
- [ ] All quantitative criteria use concrete numbers and units

### R9. Observable Verifiability
At least one verification criterion describes how to check compliance
through observable evidence: system behavior, API response, state
change, log entry, or test.

> *Reference*: ISO 29148 requires requirements to be verifiable [2,
> §6.2.2]. INCOSE establishes that verification can be performed through
> testing, analysis, inspection, or demonstration [3, §Verifiable].

- [ ] All requirements have a non-empty Verification field
- [ ] Verification describes observable behavior, not intention
- [ ] Verification criteria include expected output or error codes
- [ ] No verification criteria are circular ("will be verified during testing")

## Block C — Contextual Completeness

### R10. Self-Sufficiency
The requirement can be understood without consulting other requirements
or external documents. References to standard domain terminology are
accepted.

> *Reference*: ISO 29148 establishes that a requirement must be complete
> and understandable. Self-sufficiency does not imply explaining the
> domain, but rather that the required behavior is clear in itself [2].

- [ ] Each requirement is independently understandable
- [ ] No requirement references "the process above" or "the previous step"
- [ ] Domain terms are defined in the glossary if not standard

## Quality Gate Decision Rule

| Score | Result | Action |
|---|---|---|
| 11-12 | **PASS** | Proceed to `/speckit.plan` |
| 9-10 | **MINOR REVISION** | Proceed if deficiencies do not affect R5, R7, R8, R9 |
| ≤ 8 | **REJECT** | Reformulate before continuing |

**Blocking criteria (automatic reject regardless of total score):**
- R5 (no formal structure): the obligation cannot be identified
- R7 (no observable verb): the requirement cannot be verified
- R9 (no verifiability): the requirement cannot be used for conformance inspection

> *Reference*: Blocking criteria follow software engineering quality gate
> practice where certain properties are necessary conditions not
> compensable by other quality dimensions.
