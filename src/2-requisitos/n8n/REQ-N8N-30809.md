### ID

REQ-N8N-30809

### Nombre

Deduplicación específica por tipo de evento en disparador de Salesforce

### Tipo

Funcional

### Descripción formal

El sistema deberá diferenciar la lógica de deduplicación de registros en el nodo "Salesforce Trigger" basándose en el tipo de evento configurado (`changeType`), para evitar ejecuciones múltiples erróneas:

1.  **Eventos de Creación (`Created`)**: Para cualquier variante del disparador configurada para detectar registros creados (ej. Case, Account, Contact, etc.), el sistema deberá utilizar exclusivamente el identificador del registro (`Id`) como clave de deduplicación. La fecha de última modificación (`LastModifiedDate`) deberá ser ignorada en este contexto. Un registro solo debe activar el flujo de trabajo una vez, cuando se detecta por primera vez su `Id`.

2.  **Eventos de Actualización (`Updated`)**: Para variantes configuradas para detectar registros actualizados, el sistema deberá mantener el uso de una clave compuesta formada por el identificador del registro y su fecha de última modificación (`${Id}_${LastModifiedDate}`). Esto asegura que el flujo de trabajo se active cada vez que el mismo registro sea modificado.

### Fuente

Pull Request #30809 (https://github.com/n8n-io/n8n/pull/30809), Issue #30536 (https://github.com/n8n-io/n8n/issues/30536)

### Rationale

Anteriormente, todos los eventos del disparador de Salesforce utilizaban la clave compuesta (`Id` + `LastModifiedDate`) para la deduplicación. Debido a un margen de seguridad de 15 minutos en el sondeo, los registros recién creados permanecían en el conjunto de resultados durante ese tiempo. Si un registro era modificado poco después de su creación, su `LastModifiedDate` cambiaba, generando una nueva clave compuesta que el sistema interpretaba como un registro "nuevo", provocando que el evento `Created` se disparara múltiples veces por el mismo registro. Al separar la lógica, se garantiza que los eventos de creación se disparen exactamente una vez por registro, mientras que los eventos de actualización siguen detectando cada cambio.

### Prioridad

Alta

### Verificación

1.  **Verificación de evento `Created`**:
    a. Configurar un nodo "Salesforce Trigger" para escuchar el evento `Created` de un objeto (p.ej. `Case`).
    b. Crear un nuevo registro en Salesforce y esperar a que el disparador active el flujo de trabajo (1ª ejecución).
    c. Modificar el mismo registro en Salesforce dentro de los siguientes 15 minutos.
    d. Esperar los ciclos de sondeo correspondientes y verificar que el flujo de trabajo *no* se vuelve a activar para ese registro.

2.  **Verificación de evento `Updated`**:
    a. Configurar un nodo "Salesforce Trigger" para escuchar el evento `Updated` del mismo objeto.
    b. Modificar un registro existente en Salesforce.
    c. Verificar que el disparador activa el flujo de trabajo para esa actualización.
    d. Volver a modificar el mismo registro en Salesforce.
    e. Verificar que el disparador activa el flujo de trabajo nuevamente para la segunda actualización.
