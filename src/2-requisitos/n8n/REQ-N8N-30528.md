### ID

REQ-N8N-30528

### Nombre

Clasificación precisa de consultas SELECT en el nodo PostgreSQL

### Tipo

Funcional

### Descripción formal

El sistema deberá identificar de forma precisa si una consulta ejecutada en el nodo de PostgreSQL es una operación de lectura (`SELECT`) para determinar el formato de la respuesta. La clasificación debe ser robusta y manejar correctamente los siguientes casos:

1.  **Detección de `SELECT`**: Una consulta se considerará de tipo `SELECT` si su comando principal a nivel superior (fuera de cualquier paréntesis de subconsulta o CTE) es `SELECT`.
2.  **Manejo de CTEs y comentarios**: El sistema deberá ignorar las Common Table Expressions (CTEs) que comiencen con `WITH` y los comentarios de línea (`--`) o de bloque (`/* ... */`) al determinar el tipo de consulta. Por ejemplo, una consulta `WITH ... SELECT ...` deberá ser clasificada como `SELECT`.
3.  **Manejo de strings y literales**: El sistema deberá ignorar palabras clave como `UPDATE`, `INSERT`, etc., cuando aparezcan dentro de literales de texto (entre comillas simples, dobles o dollar-quoted strings), evitando que una consulta de lectura sea clasificada erróneamente como de escritura.
4.  **Formato de respuesta**:
    *   Si la consulta es clasificada como `SELECT` y no devuelve ninguna fila, el sistema deberá retornar un array vacío (`[]`).
    *   Si la consulta es clasificada como una operación de escritura (ej. `UPDATE`, `INSERT`, `DELETE`, `MERGE`), incluso si está precedida por una CTE, y no devuelve filas, el sistema deberá retornar el objeto `{ "success": true }`.

### Fuente

Pull Request #30528 (https://github.com/n8n-io/n8n/pull/30528), Issue #25194 (https://github.com/n8n-io/n8n/issues/25194)

### Rationale

La implementación anterior del nodo PostgreSQL (v2) utilizaba una expresión regular simple para detectar si una consulta era de tipo `SELECT`. Este método fallaba si la consulta comenzaba con una CTE (`WITH ...`) o un comentario, clasificándola incorrectamente como una operación de escritura. Como resultado, en lugar de devolver un array vacío (`[]`) cuando no se encontraban filas, devolvía `{ "success": true }`, rompiendo la lógica de los flujos de trabajo que dependían del formato de la respuesta para bifurcar su ejecución. La nueva lógica de clasificación, consciente de la sintaxis de SQL, asegura que las consultas se identifiquen correctamente y que la respuesta sea predecible y consistente.

### Verificación

1.  **Consulta `SELECT` con CTE sin resultados**:
    a. Ejecutar una consulta en el nodo PostgreSQL como `WITH t AS (SELECT 1) SELECT * FROM t WHERE 1 = 0;`.
    b. Verificar que la salida del nodo es un array vacío (`[]`).

2.  **Consulta `SELECT` con comentario sin resultados**:
    a. Ejecutar una consulta como `-- leading comment\nSELECT 1 WHERE FALSE;`.
    b. Verificar que la salida del nodo es un array vacío (`[]`).

3.  **Consulta de escritura (`UPDATE`) con CTE**:
    a. Ejecutar una consulta como `WITH cte AS (SELECT 1) UPDATE users SET name = 'test' WHERE FALSE;`.
    b. Verificar que la salida del nodo es `[{ "json": { "success": true } }]`.

4.  **Consulta `SELECT` con palabra clave de escritura en un literal**:
    a. Ejecutar una consulta como `SELECT '-- UPDATE users' WHERE false;`.
    b. Verificar que la salida del nodo es un array vacío (`[]`).
