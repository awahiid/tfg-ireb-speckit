\subsection{Los 6 hilos conductores}

Cada componente del kit ataca un fallo concreto del flujo sin IREB. Estos 6 principios garantizan que el flujo con kit mejore sistem\'aticamente al baseline:

\begin{description}
    \item[\textbf{H1 --- No alucinar contexto}:] Regla R0 bloqueante en \texttt{AGENTS.md}: Source y Rationale solo del input original. Si no hay $\rightarrow$ ``sin fuente documentada''. Verificado por \texttt{clarify} y \texttt{checklist} (R13).
    \item[\textbf{H2 --- Scope contract}:] Antes de \texttt{implement}, se define exactamente qu\'e archivos tocar, cu\'ales NO tocar, y qu\'e comportamiento implementar. Evita que el agente borre 2554 l\'ineas (medusa-e5) o genere 4238 l\'ineas para un cambio simple (n8n-e5).
    \item[\textbf{H3 --- Trazabilidad obligatoria}:] Cada artefacto (spec, plan, tarea, c\'odigo, test) debe enlazar a un REQ-ID. Sin trazabilidad $\rightarrow$ no se genera.
    \item[\textbf{H4 --- Verificaci\'on observable}:] Todo requisito debe tener al menos un criterio de verificaci\'on concreto (respuesta HTTP, cambio de estado, evento).
    \item[\textbf{H5 --- Minimalidad}:] ``Solo lo necesario para satisfacer el requisito''. Proh\'ibe refactorizar, a\~nadir dependencias o modificar configuraciones globales.
    \item[\textbf{H6 --- Contexto destilado}:] El paso \texttt{implement} recibe solo spec + scope contract + tasks ($\sim$3K tokens). El resto de la documentaci\'on IREB se genera pero no se inyecta en el prompt de c\'odigo.
\end{description}

\subsection{Derivaci\'on de MRS}

A partir de los 52 requisitos formalizados se derivaron 52 \emph{Minimal Requirement Seeds} (MRS) utilizando un script asistido por LLM. Cada MRS es un prompt m\'inimo de 3--5 l\'ineas con estructura can\'onica ``Como [ROL], quiero que el sistema [COMPORTAMIENTO] [contexto], para [MOTIVACI\'ON]''. Los MRS act\'uan como entrada replicable para el pipeline \textsc{SpecKit} en el Flow B.

\section{Ejecuci\'on del pipeline}

\subsection{Preparaci\'on del entorno}

Para cada caso, el script \texttt{preparar-caso.sh} automatiza:
\begin{enumerate}
    \item Clone del repositorio en el commit padre del merge commit (c\'odigo ANTES de la PR original).
    \item Instalaci\'on de dependencias y verificaci\'on de tests existentes.
    \item Ejecuci\'on de \texttt{specify init} para inicializar la estructura de \textsc{SpecKit}.
    \item Copia del REQ formalizado a \texttt{.specify/memory/} para el paso \texttt{specify}.
\end{enumerate}

\subsection{Ejecuci\'on manual en VS Code Copilot Chat}

Cada caso se ejecuta manualmente en Copilot Chat Agent, introduciendo los comandos \texttt{/speckit.*} en secuencia. Tras la ejecuci\'on, el script \texttt{capturar-resultado.sh} genera:
\begin{itemize}
    \item \texttt{diff.patch}: diff completo de los cambios introducidos.
    \item \texttt{summary.json}: metadata del caso (commit, l\'ineas, archivos).
    \item \texttt{full-snapshot.zip}: repositorio completo sin dependencias.
\end{itemize}

\subsection{Comparaci\'on de versiones del kit}

El Kit v1 y el Kit v2 comparten la misma base de plantillas IREB. La diferencia cr\'itica es que el Kit v2 a\~nade \texttt{AGENTS.md} con reglas universales y un paso de \textbf{scope contract} (07.5) antes de \texttt{implement}. Este scope contract lista expl\'icitamente los archivos a modificar y los archivos a no tocar, acotando el alcance de la implementaci\'on.
